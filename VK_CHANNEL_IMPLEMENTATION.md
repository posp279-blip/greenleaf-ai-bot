# ТЗ: VK как второй канал Greenleaf AI Bot

## Цель

Подключить сообщения сообщества VK к уже работающему Greenleaf AI Bot v2 на Railway, сохранив единое AI-ядро, сценарий, PostgreSQL, заявки, партнёрскую реферальную систему и веб-админку.

Telegram-бот должен продолжить работать без изменения текущего пользовательского сценария.

## Базовая ветка и ограничения

- Базовая версия: `feature/friendly-scenario-v2`.
- Не менять `main`.
- Не удалять и не упрощать Telegram webhook, polling fallback, админские callbacks, сценарий v2, AI-ответы, заявки и защиту от дублей.
- Не хранить реальные токены, секреты, group id или confirmation code в репозитории.
- Все новые переменные окружения описать в `.env.railway.example` и документации Railway.
- Изменения должны быть обратносуместимыми с существующей PostgreSQL-базой и действующими Telegram-сессиями.

## Архитектура

Нужна единая бизнес-логика и отдельные транспортные адаптеры:

```text
Telegram webhook ─┐
                  ├─ единый сценарий / AI / заявки / рефералка / БД
VK Callback API ──┘
```

Не копировать весь сценарий в отдельный `vk-engine`. Вынести минимальный платформонезависимый слой отправки сообщений, кнопок и обработки пользовательского события либо реализовать другой чистый адаптер без дублирования бизнес-логики.

## VK Callback API

Добавить endpoint:

```text
POST /api/vk/callback
```

Поведение:

1. Проверять секрет события из VK по `VK_CALLBACK_SECRET`.
2. На событие `confirmation` возвращать текст `VK_CONFIRMATION_CODE`.
3. На поддерживаемые события быстро возвращать `ok`, а обработку выполнять асинхронно, чтобы VK не повторял запрос.
4. Обрабатывать минимум:
   - `message_new`;
   - нажатия callback-кнопок VK, если используются callback-кнопки;
   - обычные текстовые payload-кнопки.
5. Логировать ошибки без токенов и персональных данных.
6. Добавить дедупликацию событий VK по `event_id` с TTL.
7. Добавить последовательную очередь обработки по ключу `vk:<userId>`, аналогично Telegram.

## Отправка сообщений VK

Создать VK API client с тайм-аутом и контролируемыми ошибками.

Переменные окружения:

- `VK_GROUP_TOKEN`
- `VK_GROUP_ID`
- `VK_GROUP_SCREEN_NAME`
- `VK_CALLBACK_SECRET`
- `VK_CONFIRMATION_CODE`
- `VK_API_VERSION`

Для `messages.send` использовать уникальный `random_id` и корректный `peer_id`.

Telegram inline/reply keyboards должны преобразовываться в клавиатуры VK. Основные кнопки сценария, меню и действия пользователя должны работать в обеих платформах.

## Реферальная система VK

У каждого партнёра остаётся единый `refCode`.

VK-ссылка партнёра:

```text
https://vk.me/<VK_GROUP_SCREEN_NAME>?ref=<refCode>&ref_source=partner
```

При первом входящем сообщении:

1. Извлечь `ref` из входящего объекта сообщения VK.
2. При необходимости поддержать безопасный fallback из `ref_source`, только если формат однозначен и покрыт тестом.
3. Нормализовать и валидировать код.
4. Найти только активного партнёра.
5. Привязать сессию кандидата к `partnerId`.
6. Не перезаписывать уже сохранённого пригласившего партнёра последующими ссылками.
7. Невалидный или несуществующий код игнорировать без ошибки для пользователя.
8. Заявка кандидата должна закрепляться за тем же партнёром, что и в Telegram.

Партнёрская команда/раздел «Как отправить» должна показывать две ссылки:

- Telegram;
- VK.

Если `VK_GROUP_SCREEN_NAME` не настроен, Telegram-ссылка продолжает работать, а VK-ссылка не показывается.

## Модель данных

Текущая схема жёстко привязана к `telegramUserId`. Сделать безопасную мультиканальную модель.

Предпочтительный вариант:

- `platform`: `telegram | vk`;
- `platformUserId`: строка или bigint в едином формате;
- уникальность сессии по `(platform, platformUserId)`;
- существующие Telegram-записи автоматически считаются `platform=telegram` и получают `platformUserId` из `telegramUserId`;
- существующий `telegramUserId` временно сохранить для совместимости, если его немедленное удаление создаёт риск;
- добавить канал/источник заявки (`telegram` или `vk`) либо гарантированно получать его через связанную сессию;
- при необходимости добавить `vkUserId` партнёру, но реферальная привязка должна работать через общий `refCode` независимо от платформы.

Обязательна миграция/инициализация, которая проходит на существующей Railway PostgreSQL без потери данных.

## Профиль и контакты

- Сохранять имя, фамилию и доступный screen name VK.
- Не считать VK screen name номером телефона.
- На этапе заявки принимать тот же контакт, который просит текущий сценарий.
- В уведомлении о заявке указывать источник: `VK` или `Telegram`.
- Уведомления партнёру и администратору пока оставлять через Telegram, используя текущую систему уведомлений.

## Админ-панель

Добавить без перегрузки интерфейса:

- источник сессии/заявки;
- VK ID или ссылку на профиль при наличии screen name;
- фильтр по каналу, если он естественно вписывается в существующий список заявок.

Редактор сценария остаётся единым для Telegram и VK.

## Совместимость сообщений

Учесть ограничения платформ:

- безопасно разбивать слишком длинные сообщения;
- не использовать Telegram Markdown/HTML там, где VK отобразит его некорректно;
- ссылки и видео должны отправляться читаемо;
- callback/payload не должен содержать непроверенные пользовательские данные;
- текущая кнопка `📤 Как отправить` и остальные названия должны совпадать с инструкциями.

## Тесты

Добавить unit/integration тесты минимум на:

1. `confirmation` возвращает код подтверждения.
2. Неверный callback secret даёт отказ.
3. `message_new` обрабатывается один раз при повторе `event_id`.
4. VK-пользователь получает/продолжает отдельную сессию.
5. Telegram-пользователь с таким же числовым ID не пересекается с VK-пользователем.
6. Валидный `ref` закрепляет активного партнёра.
7. Повторная ссылка не перезаписывает первого партнёра.
8. Невалидный `ref` не ломает сценарий.
9. Заявка VK получает правильный `partnerId` и источник.
10. Основные кнопки и шаги сценария корректно преобразуются в VK keyboard.
11. Существующие тесты Telegram остаются зелёными.

## Документация запуска

Обновить Railway-документацию:

1. Создание/выбор сообщества VK.
2. Включение сообщений сообщества.
3. Создание ключа доступа сообщества с минимальными необходимыми правами.
4. Добавление Callback API URL:
   `https://<RAILWAY_PUBLIC_DOMAIN>/api/vk/callback`.
5. Настройка confirmation code и secret.
6. Выбор необходимых событий.
7. Добавление переменных окружения Railway.
8. Проверка тестовой реферальной ссылки.
9. Проверка, что Telegram после деплоя продолжает отвечать.

## Критерии готовности

- Один сервер Railway одновременно обслуживает Telegram и VK.
- Оба канала используют один сценарий и одну базу знаний.
- Реферальные ссылки Telegram и VK закрепляют кандидата за одним партнёром по общему `refCode`.
- В админке видно источник заявки.
- Telegram не регрессировал.
- `pnpm test`, typecheck и build проходят.
- PR содержит список изменённых файлов, миграцию, инструкции настройки VK и ручной smoke-test.
